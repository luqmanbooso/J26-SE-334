1. Purpose & scope

This document specifies what HEART must do (functional requirements), how well it must do it (non-functional requirements), and the technology it is built from. It is written against the actual state of the repository, not an idealised design: §10 records what exists today and §11 records what must change and when.

Scope covers all four student components plus the shared infrastructure that joins them. It does not specify the research experiments — those live in the project research vault (research/experiments/) and are referenced only where a requirement exists to support one.

Status of this draft. Component owners C1, C3 and C4 have not yet reviewed it. Requirements attributed to their components were derived from the architecture notes, their README files and their committed code — each owner must confirm or correct their own section before this version is treated as agreed.

2. Product definition — what HEART is and is not

HEART ISHEART is NOT
A desktop application a QA engineer installs on a Windows or Linux workstationA website, a hosted service, or a SaaS product
A native desktop GUI and a Python CLI, both producing a self-contained HTML reportA web application of any kind — no SPA, no server, no node_modules, no login
A tool that drives a physically attached Android device over ADBAn Android app installed on that device
Fully offline — no screenshot or app data leaves the machineA client for a cloud vision or LLM API
A test generator, executor, oracle and repairer for other people's appsThe app being tested
The distinction that matters for the viva. There are two pieces of software in every sentence about this project: HEART (what you build, runs on the laptop) and the App Under Test (what you point it at, runs on the phone, written by somebody else — for development this is the stock Android Calculator or Dialer). Confusing them makes the entire architecture unexplainable.

The offline constraint is not a preference — it is load-bearing for the research. CLAIM-03 asserts that a localized quantized vision-language model can serve as a GUI oracle, closing the gap left by cloud-dependent visual oracles. A cloud deployment would refute the project's own claim. Everything else in the stack follows from that single decision, recorded as RDR-0009.

7. Non-functional requirements

IDAttributeRequirement
NFR-01Locality / privacyNo component may transmit screenshots, UI hierarchies, app data or telemetry to any external service during a run. This is load-bearing for CLAIM-03 — a cloud call refutes the research claim, it is not merely a preference.
NFR-02DeploymentA single workstation with Python 3.10+, Android SDK platform-tools and one attached device. No database server, no message broker, no container runtime required.
NFR-03ReproducibilityA run must be repeatable from a recorded seed and profile. Stochastic components must accept an explicit RNG seed — without this, the ablation experiment cannot isolate the coupling term.
NFR-04Experimental validityThe execution driver, oracle, device and time budget must be held constant when comparing input generators; only the generator may vary.
NFR-05ExplainabilityCognitive model parameters must be inspectable and literature-traceable rather than learned, so that any generated behaviour can be defended. (Per RDR-0001.)
NFR-06Testability offlineEvery component must be exercisable against saved fixtures with no device attached — required for CI, and the fallback demonstration path.
NFR-07PortabilityWindows and Linux. Paths must not assume a drive letter or a POSIX root.
NFR-08Interface stabilityEvery inter-component payload carries a schema_version and validates against a published JSON Schema before use.
NFR-09ObservabilityEvery run writes a timeline that permits a failure to be traced back to the input, stress state and environment condition that produced it.
NFR-10PerformanceThresholds not yet set. Oracle inference latency per action and perturbation overhead must be measured before targets are fixed — no number is asserted here because none has been measured.

8. Technical stack specification

This section is prescriptive — it states the stack HEART should be built on, chosen on merit rather than inherited from what happens to be in the repository today. §10 records the current state and §11 the delta. Decided in RDR-0009 and RDR-0010.

Three principles behind every choice below. (1) Offline by construction — nothing may call out to a network, so no CDN, no hosted model, no cloud database. (2) Explainable in a viva — prefer a boring library you can describe over a clever one you cannot. (3) One process, one language — four students have one semester; every extra runtime is a tax paid at integration time.

8.1  Languages & runtime

ConcernChoiceVersion floorWhy this one
Application languagePython3.11The only language with first-class libraries for all four problem domains at once — device automation, numerical sampling, local model inference and NLP. 3.11 for the faster interpreter and far better tracebacks.
Query languageSQL — SQLite dialect—The failure ↔ behaviour ↔ environment correlation in FR-S-04 is a join. Writing it as SQL is shorter and more defensible than reimplementing joins in Python.
Report templatingJinja23.1Renders the static HTML report. Already the de facto Python templating engine.

Shelladb via subprocess—Platform-tools is an external binary, not a Python package. Treat it as a system prerequisite.

8.2  Database & persistence

ConcernChoiceRationale
DatabaseSQLite 3 via the stdlib sqlite3 moduleOne file on disk, zero servers, zero configuration, ships inside Python. A single-user offline desktop tool must not require a running database process — that would make installation harder than the tool itself. Handles this data volume without effort.
Access layerHand-written SQL + Pydantic v2 modelsFive tables do not justify an ORM. Raw SQL is completely explainable under questioning; ORM-generated queries are not. Pydantic validates rows on the way in and out, so the same model serves as the DB row and the interface contract.
MigrationsA schema_version table + numbered .sql filesAlembic and SQLAlchemy are a heavy dependency for a schema that changes a handful of times. Numbered scripts are auditable and trivial.
Binary artifactsFilesystem directory; DB stores the pathScreenshots must never be written into the database as blobs — the file would grow to gigabytes and become slow and unbackupable. runs/<run_id>/screenshots/<action_id>.png.
Interchange formatJSON validated by JSON SchemaEvery cross-component payload (§9), each carrying schema_version.
Considered and rejectedPostgreSQL · SQLModel · SQLAlchemy · MongoDBPostgreSQL needs a server (RDR-0009 supersedes it). SQLModel/SQLAlchemy add an ORM layer and a dependency tree for no benefit at this scale. MongoDB is schemaless, which is the opposite of what NFR-08 requires.

One run_id and one t_ms axis across all six tables is what makes FR-S-04 a single query rather than a research project of its own.

8.4  Machine learning & inference

Two runtimes, deliberately — not one. An earlier draft of this document proposed Ollama for both C3 and C4. That was wrong: C3's design includes a fine-tuning lane (Rico/Themis → fine-tune → quantize → deploy) and Ollama does not fine-tune. A model C3 has adapted must be trained and quantized in the Hugging Face ecosystem, so C3 lives there end to end. C4 performs inference only on a general instruct model and keeps Ollama.
ConcernChoiceFloorRationale
C3 — model & runtimetransformers + accelerate4.40Loads Qwen2-VL, runs the fine-tune, and serves inference from the adapted checkpoint. The only path that supports all three stages of C3's offline lane.
C3 — fine-tuningpeft (LoRA)0.10Adapter-based tuning fits a 2B vision-language model on student hardware; full fine-tuning does not.
C3 — quantizationbitsandbytes (or AWQ)0.434-bit/8-bit load so the adapted model runs locally. bitsandbytes is the lower-friction option; AWQ gives better quality per bit if time allows.
C4 — runtimeOllama—Inference only, on a stock instruct model, for test-step synthesis. One binary, local HTTP endpoint, no Python model-loading code. Keep it.
C4 — semantic matchingsentence-transformers2.7SBERT embeddings for locator healing — matching UI elements by meaning, not string equality.
Tensor backendtorch2.2Shared by C3 and sentence-transformers. CPU build is sufficient for inference; a CUDA build makes C3's fine-tune far more comfortable.
Considered and rejectedOllama for C3—Cannot fine-tune, and serving a custom adapted checkpoint through it adds a conversion step for no benefit. Rejected once the fine-tuning lane was accounted for.

Citation note: the Qwen2-VL, LoRA and AWQ literature notes are all currently verified: false. The tools may be used; the papers may not be cited in any deliverable until someone opens the PDFs and confirms them.

8.6  User interface

Three entry points, one orchestrator, no web stack. A native desktop GUI for interactive use, a CLI for headless and CI runs, and a generated HTML report for results. All three call the same in-process Python functions — there is no server, no browser and no JavaScript anywhere in the product.

Keep the GUI thin. Campaign setup, start/stop, live status, and a button that opens the report. The expensive parts of a results UI — sortable failure tables, the screenshot gallery with C3's overlay regions, drill-down into a run — belong in the report, not in the window. Built once in HTML and SVG they are also portable: a report can be emailed, archived and attached to the thesis, whereas evidence locked inside an application only its author can run is weak evidence. If someone proposes building the failure gallery inside the GUI, the answer is that it goes in the report.

ConcernChoiceFloorRationale
Desktop GUIcustomtkinter5.2Themed widgets over Tk, which ships with Python. Pure Python, no extra runtime, and a PyInstaller bundle in the tens of megabytes rather than the hundreds — itself part of the commercialisation argument. Owned by C1.
Tables in the GUItkinter.ttk.TreeviewstdlibCustomTkinter has no table widget; ttk's Treeview is a genuine sortable tree-table and costs nothing. One table is enough — recent runs. Anything richer goes in the report.
Live chart in the GUImatplotlib via FigureCanvasTkAgg3.8The stress timeline redrawn at ~1–2 Hz, which Tk handles comfortably. Reuses the same figure code that produces the report and thesis figures — one plotting stack, three outputs, no duplicated chart logic.
CLI frameworktyper0.12Commands are type-annotated Python functions; help and parsing generated from the signatures. The headless path, and what CI calls.
Live terminal viewrich13.7A Live panel showing cognitive state, stress s, actions executed and failures found — the CLI's equivalent of the GUI status panel, for runs with no display attached.
Report renderingjinja2 + embedded SVG + hand-written CSS3.1One report.html: figures inlined as SVG, CSS inlined in a <style> block. Opens anywhere, survives being emailed, prints to PDF, needs no server and no internet.
CSS frameworkNone—Tailwind and Bootstrap each mean a CDN link or a build step. Both break NFR-01.
Charting libraryNone — matplotlib pre-renders—Charts are generated as SVG and embedded. No Chart.js, no Recharts, no runtime JavaScript.
Considered and rejectedPySide6 + pyqtgraph—Technically the strongest option — QGraphicsView is purpose-built for screenshot-plus-overlay, QTableView scales to thousands of rows, pyqtgraph beats matplotlib for real-time plots, and PySide6 is LGPL so commercial use is clean. Rejected because the thin-GUI split removes the need for all three, at a cost of a ~150–250 MB bundle and a steeper learning curve. This is the option to switch to if the GUI ever becomes the product and the report becomes secondary.
Also rejectedDear PyGui · Flet · NiceGUI / Streamlit / Gradio—Dear PyGui has the best live plotting but an unusual immediate-mode model and an engineering-tool look. Flet bundles a Flutter runtime. The browser-based toolkits all run a local server — excluded by RDR-0010.

11. What must change

Ordered by consequence. None of §11.2–§11.5 should be attempted before PP1 on 22 October — a repository-wide refactor that week would break every member's demonstration.

11.1  Close the measurement gap (blocking a research claim)

The adaptation pillar requires a signal describing how the app is behaving, and nothing produces one. Two options, not mutually exclusive:

  • C1 implements FR-C1-07 — the App State Monitor polls dumpsys gfxinfo and logcat and publishes real telemetry. Correct long-term, but it is C1's schedule, not C2's.
  • C2 measures its own (RDR-0008, adopted) — wall-clock time from tap dispatch until the UI hierarchy changes, plus a no-change flag. ~40 lines on the existing ADB bridge, no new dependency, and it is the ui_delay_ms field of the contract.

Adopting the second unblocks C2 immediately and leaves the first as a C1 improvement that enriches the signal rather than enabling it.

11.2  Make the components importable

Folder names containing spaces and parentheses are not valid Python module names. Today the four components physically cannot import one another; each runs only as a loose script from inside its own directory. No orchestrator can be written until this is fixed.

11.3  Collapse the three ADB wrappers into one

env testing/core/adb_client.py, self heal telemetry/core/adb_client.py and biometry/bridge/adb_bridge.py solve the same problem three ways and are already diverging. Replace with a single src/common/adb.py providing device discovery, hierarchy dump, element lookup, tap/swipe injection and logcat reading. C2's bridge is the most complete starting point.

11.4  Build the shared layer and give it an owner

The orchestrator, execution driver and results store are the entire integration story and have no owner. Minimum viable versions:

  • Results store — one SQLite file, tables run, event, verdict, env_timeline, stress_timeline, plus an artifact directory for screenshots. A day's work and it unblocks FR-S-04 correlation.
  • Execution driver — thin wrapper over the shared ADB module that accepts a motion-event stream and emits an action-complete event. Must be the only path to the device so that NFR-04 holds.
  • Orchestrator — a plain Python module invoked by the CLI (heart run --profile rushed --app com.x). No HTTP layer at all — the engines are called in-process, which removes a server, a port and an entire class of integration bug.
  • Report generator — Jinja2 template plus matplotlib SVG, producing one self-contained report.html per run. Roughly a day's work, and it replaces the dashboard as the project's presentation layer (RDR-0010).

11.5  Put every interface behind a versioned schema

Promote C4's c3_interface pattern to a shared src/common/contracts/: a Pydantic model and JSON Schema per interface in §9, each with schema_version, each with a mock producer. This is what allows C3 to be behind without blocking C4, and C1 to be behind without blocking C2.

The one stack change worth making before PP1. C2 samples from the stdlib random module, which seeds a single hidden global generator. NFR-03 requires a run to be reproducible from a recorded seed, and the coupling ablation compares two runs that must differ only in the engine variant. That comparison is not sound unless both runs draw from an explicitly seeded, independent generator — numpy.random.default_rng(seed) passed into the sampler. It is roughly a thirty-minute change, it is in C2's own code, and it is the difference between an experiment that proves something and one that does not.
Everything else can wait, and should. Fourteen of the eighteen rows above are "not built yet" or already aligned. Of the four genuine divergences, two are resolved by stopping work (the SPA and the HTTP server), one is a thirty-minute fix, and one — uiautomator2 — is only needed for gesture distortion, which is a should-have and not in the pre-PP1 plan. No refactor is required before 22 October.

Out of scope

  • iOS, tablet and wearable targets — Android only.
  • Multi-user, authentication, tenancy or any hosted deployment.
  • Any web user interface. No SPA, no HTTP server, no JavaScript toolchain — descoped by RDR-0010. A native desktop GUI is in scope and is C1-owned.

  • Any mobile application written by this team. There is none, by design.

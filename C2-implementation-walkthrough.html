Component 2 · Code-level walkthrough

How C2 touches an app

Every step from "a phone is plugged in" to "a distorted tap landed and the engine got angrier about it" — read out of the actual source, with file and line references.

Repo: J26-SE-334/biometry Read 2026-10-16 · updated 2026-10-17 against the live-device build Ground truth: the code, not the notes

The short answer to "how does it know what buttons to touch" is that it asks Android. Android's own accessibility layer will hand over every widget on the current screen, with pixel bounds, and C2 filters that list down to things a finger would plausibly aim at. Choosing which of them to press is, today, deliberately dumb — round-robin, or a name lookup. The research work is in the step after: how the finger lands on the chosen widget, and how that changes as the app misbehaves.

01The loop in one picture

Six things happen per action, in a cycle. The screen is read, a target is chosen, the current stress value bends the touch away from the target's centre, the touch goes out over ADB, the probe reads the frame statistics the device kept while the action landed, and what they say about rendering becomes a provocation value that moves the cognitive state — which sets the stress for the next action.

The one arrow that makes this a research contribution rather than a tap script is the orange one: the app's behaviour feeding back into how the next touch is physically performed.

02Seeing the screen — the dump

C2 never looks at pixels to find a button. It asks Android's UIAutomator service to serialise the whole view tree to a file on the device, then reads that file back. Two shell commands:

common/adb.py : 160–184 · AdbDevice.dump_hierarchy()

with DeviceLock(self.serial, self._lock_timeout):
    subprocess.run(self._argv(["shell", "uiautomator", "dump",
                               "/sdcard/window_dump.xml"]), ...)
    raw = subprocess.run(self._argv(["exec-out", "cat",
                               "/sdcard/window_dump.xml"]), ...).stdout
self._dumps += 1
text = raw.replace("\r\r\n", "\n").replace("\r\n", "\n")
match = re.search(r"(<hierarchy[\s\S]*?</hierarchy>)", text)
if not match:
    raise RuntimeError("no <hierarchy> element in the device dump")

Four implementation details in those eight lines that matter more than they look:

  • exec-out cat rather than adb pull — the bytes come back on stdout, so nothing lands in the working directory to be clobbered by another component.
  • The line-ending scrub exists because ADB mangles \n into \r\r\n on some hosts, which breaks the XML parser.
  • The regex throws away anything UIAutomator printed around the XML (it prints a status line), keeping only <hierarchy>…</hierarchy>.
  • Everything runs under a cross-process file lock keyed by device serial. Three components in this project drive the same phone from three separate OS processes, and uiautomator dump is exclusive — so a thread lock would not have been enough.

The result is cached with a timestamp. dump_hierarchy(max_age_s=0.3) hands back the previous dump if it is younger than 300 ms instead of paying for another one; max_age_s=0.0, the default, always forces a fresh read.

03Turning XML into targets

A dump is a tree of <node> elements, each carrying a bounds attribute of the form [x1,y1][x2,y2] in device pixels, plus text, content-desc, resource-id and clickable. The parser reduces each node to the five numbers the engine needs and a human-readable name.

biometry/bridge/hierarchy.py : 48–64 · the name fallback chain

text  = (node.get("text") or "").strip()
desc  = (node.get("content-desc") or "").strip()
resource_id = node.get("resource-id") or ""
label = text or desc or resource_id.rsplit("/", 1)[-1] or "unnamed"

That label becomes element_id, and it is what appears in the output timeline as target_element_id. It is a convenience for reading a run back, not an identity — two unnamed widgets both become "unnamed".

Three functions make up the whole of this file, and none of them touches a device:

Why it is built this way

Accepting a saved file as readily as a live dump is what lets the entire engine run with no phone attached, against real screen layouts. That matters for more than convenience: real screens have a spread of widget sizes, and the spatial model's whole width-dependence only gets exercised by that spread. One synthetic rectangle exercises none of it.

04Picking which target to press

This is the part that is intentionally not clever, and it is worth being blunt about it. Three strategies exist in the repository, and none of them understands what a button means.

a. Round-robin over everything tappable

What the live entry point and the offline demonstration both do:

biometry/run_live_adaptive.py : 33–37, 50–52

bridge  = ADBBridge(device_id=args.device)
targets = tappable_targets(parse_hierarchy(bridge.dump_ui_hierarchy()))
if not targets:
    raise SystemExit("no tappable elements on the current screen")

for i in range(args.actions):
    target = targets[i % len(targets)]
    record = controller.act(target.as_target())

Sixty actions over eighteen targets means each one gets pressed three or four times, in dump order, which is roughly top-to-bottom reading order of the view tree.

Consequence to know about

The target list is read once, before the loop, and never refreshed. If a tap navigates the app to another screen, the engine carries on tapping the coordinates of widgets that are no longer there. For a keypad that is fine — the dialer keypad does not move — and for the stress experiment it is arguably the point, since the independent variable is the touch distortion rather than the route through the app. It is not fine for anything that navigates, and it is the first thing to fix before a real hardware run.

b. Lookup by name

When a script needs a specific button, it asks for one by text. The matcher is a substring test, case-insensitive, across three attributes at once:

biometry/bridge/adb_bridge.py : 39–48 · find_element_by_text()

needle = text_query.lower()
for node in self.dump_ui_hierarchy().iter("node"):
    text   = node.get("text", "")
    desc   = node.get("content-desc", "")
    res_id = node.get("resource-id", "")
    if needle in text.lower() or needle in desc.lower() or needle in res_id.lower():
        return self._parse_bounds(node.get("bounds", ""), text or desc, res_id)
raise ValueError(f"UI element matching {text_query!r} not found on the current screen.")

First match wins, in document order. Because vendors label the same dial-pad key differently, the dialer demo tries a ladder of queries per digit and takes whichever hits first:

biometry/demo_live_dialer.py : 25–38

word_map = {"0":"zero", "1":"one", ..., "9":"nine"}
queries  = [digit, word, f"digit_{digit}", f"key_{digit}"]
for query in queries:
    try:
        return bridge.find_element_by_text(query)
    except ValueError:
        continue
raise ValueError(f"Could not locate dialer key for digit '{digit}' on screen.")

So pressing 7 tries "7", then "seven", then "digit_7", then "key_7". Each attempt costs a hierarchy dump, and a substring search is loose enough to match the wrong thing — "1" matches a phone number containing a 1 before it matches the key, which is visible in the committed dump where one target is labelled "1 (590".

c. Visual verification

demo_live_pixel_detector.py exists purely so a human can check the geometry. It captures screencap alongside the dump and draws every detected element's bounding box in green, with a red crosshair at the centre the engine would aim at, writing detected_pixels.png. It does no detection from the image itself — the boxes come from the XML.

The honest scope line

There is no goal-directed target selection anywhere in C2, and that is by design rather than by omission. The gap this component addresses is about adapting how an action is performed, not which action is chosen; existing testing tools already choose actions from feedback. A sequence of intended actions is meant to arrive from outside — that is the IF-Orchestrator-to-C2 interface, which is specified and not implemented. Until it exists, round-robin is the stand-in.

05One action, seven steps

Everything above is setup. This is the engine. AdaptiveFeedbackController.act(target) is 35 lines and does seven things in a fixed order.

biometry/engine/controller.py : 87–124 · act(), abridged

stress = self.cognitive.stress                      # 1. read the mood
prev_x, prev_y = self._previous_point or (None, None)
tap = self.simulator.simulate_tap(                  # 2. bend the touch
    target["x"], target["y"], target["width"], target["height"],
    stress, prev_x=prev_x, prev_y=prev_y)

before = self.probe.read_signature()                # 3. fingerprint the screen
self.dispatch(tap["actual"]["x"], tap["actual"]["y"], tap["delay"])   # 4. touch
observation  = self.probe.observe(before=before)    # 5. time the reaction
provocation  = self.probe.provocation(observation)  # 6. score the annoyance

state_before = getattr(self.cognitive, "state", None)
self.cognitive.update(provocation)                  # 7. move the mood

record = ActionRecord(...)                          #    write it all down
self.timeline.append(record)
self._previous_point = (tap["actual"]["x"], tap["actual"]["y"])
return record
  1. Read the mood. self.cognitive.stress, a float in [0,1]. Read, never computed here.
  2. Bend the touch. The target's centre and size go in; a landing point, a delay and a hit flag come out. Covered in §06 and §07.
  3. Fingerprint the screen before touching it, so there is something to compare against afterwards.
  4. Dispatch. dispatch is an injected callable taking (x, y, pre_delay). In production it is AdbDispatcher; in tests it is a lambda that records and returns.
  5. Time the reaction by polling the fingerprint until it changes or the timeout expires.
  6. Score the annoyance — map that measurement onto [0,1].
  7. Move the mood. One Markov step, then the stress eases towards the new state's target. The state recorded is the state the action was performed in (state_before), not the one it caused.

The landing point is remembered as _previous_point, which is what gives the next action an approach direction. The engine therefore models a finger travelling between the places it actually landed, not between the places it was aiming.

The seam that makes it testable

dispatch, probe, cognitive and clock are all constructor arguments. There is no branch anywhere in the controller for "offline mode". An offline run and a live run differ only in which objects were passed in — which is why the offline path is a credible stand-in rather than a second program.

06Where the finger lands

Given a target centre, a width and a height, and a stress value, produce a point. Four stages.

Stage 1 — the approach angle

θ is the direction of travel from the last landing point to this target: atan2(dy, dx). With no previous point it defaults to π/4 (a bottom-right thumb reach); if the finger is already exactly on the target, a uniform random angle stands in for resting drift.

Stage 2 — how wide the scatter should be

The spread before stress comes from the FFitts variance decomposition: an observed touch spread is a relative term that grows with the target plus an absolute finger-imprecision floor that does not.

biometry/models/spatial.py : 59–64 · base_sigma()

width_mm = min(width, height) / self.px_per_mm      # the dimension deciding a hit
sigma_relative_mm = self.relative_coeff * math.sqrt(width_mm)
sigma_mm = math.hypot(sigma_relative_mm, self.sigma_absolute_mm)
return sigma_mm * self.px_per_mm

Three constants, two of them calibrated against published 2D touch data rather than chosen: sigma_absolute_mm = 1.50, relative_coeff = 0.493 (the k in k·√W), and px_per_mm = 16.0, which approximates a ~400 ppi phone. The provenance and the goodness-of-fit live with EXP-03 on the research side.

Because the floor does not shrink with the target while the relative term grows only as √W, small targets are effectively smaller than their nominal bounds — which is the mechanism behind miss rate rising as widgets shrink. Note that lengths are millimetres internally; px_per_mm is the only bridge to pixels, and it must be measured per device or the calibration means nothing.

Stage 3 — split across two axes, then rotate

The offset is drawn in the frame of the approach vector: one axis along travel (u), one lateral (v), the lateral one narrower by aspect_ratio = 0.45. Stress widens both, the major axis more than the minor. Then a plain rotation matrix turns (u,v) into screen coordinates.

biometry/models/spatial.py : 84–101 · generate_touch(), the core

sigma_base = self.base_sigma(width, height)
sigma_u = sigma_base * self.ANISOTROPY_NORM * self.coupling.factor(stress, 1.00)
sigma_v = (sigma_base * self.ANISOTROPY_NORM * 0.45) * self.coupling.factor(stress, 0.48)

delta_u = self.rng.normal(0.0, sigma_u)
delta_v = self.rng.normal(0.0, sigma_v)

dx = delta_u * math.cos(theta) - delta_v * math.sin(theta)
dy = delta_u * math.sin(theta) + delta_v * math.cos(theta)
return target_x + dx, target_y + dy, theta

ANISOTROPY_NORM = √(2/(1+r²)) = 1.2897 exists so that squashing one axis does not quietly shrink the delivered bivariate spread below the calibrated value. With it, SDxy = √((σ_u² + σ_v²)/2) comes back out equal to base_sigma at zero stress. Unit tests could not catch the omission, because every axis test still passed; the distribution-level realism check did.

All of the stress scaling goes through one object, StressCoupling, which is a frozen dataclass holding a single number:

biometry/models/coupling.py : 22–25

def factor(self, stress, sensitivity=1.0):
    if not 0.0 <= stress <= 1.0:
        raise ValueError(f"stress must be in [0,1], got {stress}")
    return 1.0 + self.alpha * sensitivity * stress

With alpha = 2.5, that is the whole coupling: every distortion module multiplies its nominal spread by 1 + 2.5·sensitivity·s. Modules differ only in their sensitivity weights. Setting alpha = 0 disables stress everywhere in the engine at once, which is exactly what the noise-only ablation variant needs.

Stage 4 — did it land on the thing?

The hit test is an axis-aligned box check against the nominal bounds, and the error is plain Euclidean distance from the centre:

biometry/simulation/simulator.py : 43–54

error_distance = math.sqrt((actual_x - target_x)**2 + (actual_y - target_y)**2)
half_w, half_h = width / 2.0, height / 2.0
is_hit = ((target_x - half_w <= actual_x <= target_x + half_w) and
          (target_y - half_h <= actual_y <= target_y + half_h))

This is the engine's own bookkeeping, not the device's verdict. The tap is dispatched to the distorted coordinates regardless, so on a real phone the app decides what was actually pressed — possibly the neighbouring key, possibly nothing. hit_flag records whether the engine believes it hit, which is what makes miss rate measurable offline.

Reproducibility

BiometricSimulator.__init__ creates one seeded numpy.default_rng and hands the same generator to both models, and one StressCoupling and hands that to both too. A whole run is therefore reproducible from seed alone, and two engine variants can be compared on identical random draws. No module ever calls module-level random.

07When the finger moves

Each action also carries a pre-action delay, drawn from a log-normal — positive by construction, right-skewed at every stress level, which a Gaussian cannot be. Stress does two separate things to it through the same coupling term:

biometry/models/timing.py : 42–47 · generate_delay()

median    = self.base_time / self.coupling.factor(stress, 0.60)   # haste
sigma_log = self.shape * self.coupling.factor(stress, 1.20)       # inconsistency
delay = self.rng.lognormal(mean=math.log(median), sigma=sigma_log)
return max(self.MIN_DELAY, delay)                                 # 0.05 s floor

The median is divided by the factor, so a hurried user acts sooner; the log-space spread is multiplied, so a hurried user is less consistent. The right tail survives both, which is how hesitation and haste coexist in one distribution rather than needing two modes. The 50 ms floor is there because the device coalesces events below it.

From base_time = 0.3, shape = 0.18 — again arithmetic from the formula:

0.05 calm0.279 s0.2070.285 s
0.45 impatient0.179 s0.4230.196 s
0.90 frustrated0.128 s0.6660.159 s

The delay is not slept off inside the model. It is returned as a number, travels through act() as tap["delay"], and is slept off by whoever dispatches — ADBBridge.execute_tap does time.sleep(pre_delay) immediately before input tap. In tests the dispatcher ignores it and the clock is fake, so a 120-action run completes instantly.

Two explicit behaviours sit on top of the distribution since 2026-10-17. hesitation_gap() occasionally adds a long pause — its probability rises with stress through the same coupling, and its length is a multiple of the resting median, so it reads as a stall rather than a slow action. rage_burst() occasionally repeats the tap at the same point with 80–160 ms gaps; the chance of a burst, not the taps themselves, is what stress scales. Both travel into the timeline as hesitation_s and rage_taps. Fitts movement time remains unimplemented.

08Reading the app's reaction

The loop needs a number saying "the app just behaved badly". The agreed interface promises latency, frame drops and ANR flags from C1, and nothing produces them, so C2 measures the app's reaction itself. How it measures changed on first contact with hardware, and the story is worth keeping because the discarded instrument explains the one that replaced it.

The first instrument, and why it died

The first probe timed the wall-clock gap between dispatching a touch and the UI hierarchy changing, by fingerprinting the screen and polling the fingerprint in a loop:

biometry/bridge/latency_probe.py · observe() — now the fallback

while True:
    signature, cost = self._timed_read()      # hash of a uiautomator dump
    if signature != before:
        return ...                            # changed: the gap is the delay
    if elapsed >= self.timeout:
        return ...                            # gave up
    self.sleep(self.poll_interval)            # look again in 80 ms

The probe times its own reads and raises contended when one read costs more than the poll interval — at which point the measurement is about the tooling, not the app. On the first hardware run that flag fired on all 25 samples: a uiautomator dump costs about 2413 ms on the test device, while a calculator tap responds in roughly 50 ms. The ruler's smallest mark was fifty times the thing being measured, so every answer came back as either "already changed" or "timed out", nothing in between. No value of poll_interval or timeout fixes that — the cost is in looking at all.

The replacement: ask the renderer, not the screen

Android already measures its own rendering. dumpsys gfxinfo <package> reports, per process, how many frames were drawn, how many missed their deadline ("janky"), and the frame-time percentiles — and reading it costs about 58 ms, near the 28 ms bare-ADB floor. Passing reset zeroes the counters as it prints, which turns two reads into a measurement window:

biometry/bridge/frame_probe.py · read_signature() / observe()

def read_signature(self):
    self.snapshot()          # zero the counters; discard the reading
    return None              # there is no fingerprint — the window is open

def snapshot(self):
    text = self.device.shell("dumpsys", "gfxinfo", self.package, "reset")
    return FrameStats.parse(text), cost

def observe(self, before=None):
    window, cost = self.snapshot()           # one read, no loop
    stalled = window.total_frames == 0       # the app did not react at all

Three readings that are not what they look like

All three were found by running it, not by reading the docs. Without reset the percentiles are lifetime figures — a first run showed p95 barely moving across forty actions because it described the whole process, not the action just performed. An empty window reports 4950 ms in every percentile — the top histogram bucket used as an empty-set sentinel, not a latency anyone measured; ui_delay_ms returns None for a stalled window rather than report it. And a jank ratio over a handful of frames is noise — one janky frame out of two is not a 50% jank rate; below MIN_FRAMES_FOR_JANK = 8 the ratio is not computed at all.

From rendering to annoyance

biometry/bridge/frame_probe.py · provocation()

if observation.stalled:
    return 1.0                                # nothing rendered: maximal
slowness = (frame_ms - self.smooth_ms) / (self.intolerable_ms - self.smooth_ms)
jank     = observation.jank_pct / self.jank_tolerance
return min(1.0, max(0.0, max(slowness, jank)))

Zero at one 60 Hz frame (smooth_ms = 16.7), one at a visible stutter (intolerable_ms = 250) or at 20% janky frames (jank_tolerance = 0.20), whichever is worse; a window in which nothing rendered at all is maximally provoking. This maps what a user perceives — stutter, sluggishness, a dead screen — rather than a point latency below their perceptual floor. The three thresholds are explicit constructor arguments and are the section's honest placeholders: flagged in the source as pending calibration.

The prediction that paid out

An earlier revision of this section warned, before any device was attached, that each poll forces a fresh dump, that a dump "costs a few hundred milliseconds on real hardware", and that contended would likely fire on every observation. That is exactly what happened — except the dump cost 2413 ms, worse than feared. The contended flag, built for a different failure, is what surfaced it instead of letting it average into the stress curve. The fix was not a faster poll; it was the realisation that the platform already measured what the poll was reconstructing. LatencyProbe is kept only for devices without usable gfxinfo, and the decision trail is RDR-0008 on the research side.

09Escalating the mood

Three states on a ladder, one rung per transition, and a stress value that eases towards the current state's target rather than jumping to it.

biometry/models/cognitive.py : 85–96 · update()

p_up, p_down = self.transition_probabilities(provocation)
draw = self.rng.random()
if draw < p_up:
    self.state = LADDER[self.rung + 1]
elif draw < p_up + p_down:
    self.state = LADDER[self.rung - 1]

target = TARGET_STRESS[self.state]
self.stress += (target - self.stress) * min(1.0, self.ease * dt)
self.stress = float(np.clip(self.stress, 0.0, 1.0))
return self.stress

One random draw decides all three outcomes — escalate, settle, or stay — which keeps the whole transition reproducible from one seed. The easing is what makes the stress timeline read as a curve rather than a staircase, and it is also why the state recorded alongside an action is the state the action was performed in: by the time update() has run, the mood belongs to the next action.

One ActionRecord per action, appended to a StressTimeline, written as JSON. Field names deliberately match the IF-C2-to-Store contract so the timeline persists without translation. Here is record zero of the committed offline run, verbatim:

The contract has two known gaps: there is no schema_version field and no JSON Schema, and the shared store it is supposed to write into does not exist yet — so today the consumer is a file path.

12The device layer

Below everything above sits one file, common/adb.py, which is now the only ADB connection in the repository. Three components used to open their own, with nothing coordinating them. The consequence was not just duplication: a dump issued by one component while the probe was timing the device turned that timing into a measurement of contention.

Exclusive access

A lock file in the system temp directory, keyed by device serial, taken with flock (or msvcrt.locking on Windows) plus a thread lock. The components run as separate OS processes, so a thread lock alone could not serialise them.

One dump per cycle

dump_hierarchy(max_age_s=…) returns a cached dump when a fresh enough one exists, so N callers in a cycle cost one dump instead of N. dump_count exposes the real cost an instance imposed.

No silent fallback

A missing adb binary, no device, an ambiguous choice of two devices — each raises NoDeviceError with an actionable message. A run that injected nothing must never be indistinguishable from a clean one.

No shell strings

Every command is an argument list. A locator containing a semicolon stays one argument instead of becoming a second shell command.

ADBBridge is now a thin adapter over that: dump_ui_hierarchy() returns an ElementTree root, find_element_by_text() does the name lookup, execute_tap() sleeps the pre-delay then taps. And two small adapters in bridge/device.py are the entire difference between an offline and a live run:

biometry/bridge/device.py · the whole file, minus docstrings

class AdbDispatcher:
    def __init__(self, bridge):
        self.bridge = bridge
        self.dispatched = 0
    def __call__(self, x, y, pre_delay=0.0):
        self.bridge.execute_tap(x, y, pre_delay)
        self.dispatched += 1

    def swipe(self, path, duration_s, pre_delay=0.0):
        self.bridge.execute_swipe(path, duration_s, pre_delay)
        self.dispatched += 1

def live_probe(bridge, **kwargs):
    """Fallback for devices without gfxinfo — see §08."""
    return LatencyProbe(lambda: hierarchy_signature(bridge), **kwargs)

The Driver that isn't there

The group architecture puts a shared Test Execution Driver between every engine and the phone: C2 decides a touch and writes it as ordered motion events; the Driver performs it. That component was never built — and a list of events nobody performs does nothing: no tap lands, the app never reacts, the probe has nothing to read, the adaptive loop cannot close. So AdbDispatcher above is a deliberate 15-line stand-in for it, carrying taps and straight swipes over adb shell input, while engine/events.py keeps producing the formal hand-off format the real Driver will consume.

The separation survives because the controller never knows who performs — dispatch is an injected callable:

AdaptiveFeedbackController(..., dispatch=AdbDispatcher(bridge))   # today
AdaptiveFeedbackController(..., dispatch=the_real_driver)         # the day it exists
AdaptiveFeedbackController(..., dispatch=recording_stub)          # in all 167 tests

What the stand-in costs, precisely: one feature, zero claims. input swipe draws straight lines, so a synthesized gesture's curved, trembling path reaches the device as its endpoints and duration — the curve itself is preserved in the timeline and the event list, waiting for a sendevent/uiautomator2 driver to replay it. Nothing in the demo, EXP-02 or CLAIM-01 depends on that. The real Driver has exactly three future customers: C2 (curved-path replay with real timing fidelity — input costs a ~28 ms round trip per event, so burst gaps are approximate), C4 (replaying healed scripts is executing recorded event streams), and the evaluation (EXP-01 must hold the execution instrument constant across input generators). For everything the current experiments need, nobody needs it — which is why carrying the stand-in, rather than waiting, was the right call.

13Running it

Both entry points run from inside biometry/, because the imports are package-relative to that directory.

No device required

cd J26-SE-334/biometry
python demo_adaptive_loop.py

Targets come from the committed window_dump.xml; the app under test is a DegradingApp stub scripted to stay responsive for the first quarter of the run, degrade to roughly 25 poll intervals of lag by 70%, then recover. The clock is fake, so it finishes instantly. It runs the adaptive and static arms on the same seed and writes both figures plus the timeline JSON into results/.

Against a real device

adb devices                      # must list exactly one, or pass --device
cd J26-SE-334/biometry
python run_live_adaptive.py --actions 60 --seed 2026 --profile rushed
python run_live_adaptive.py --actions 60 --seed 2026 --static --stress 0.05

Flags are --actions, --seed, --device, --static, --stress, --profile, --package, --px-per-mm, --out. When --package or --px-per-mm is omitted it is read from the device itself — the foreground window and wm density respectively — because the spatial calibration is in millimetres and means nothing at an assumed scale. Launching the app under test is the operator's job.

Prerequisite

The repository carries its own interpreter at J26-SE-334/.venv with numpy and scipy installed; run everything through it (../.venv/bin/python from inside biometry/). adb comes from Android platform-tools.

15What's left to build

Of the ten items this list held on 2026-10-16, seven are done — the interpreter, the per-device px_per_mm, the probe (replaced rather than fixed, §08), the first hardware runs, the gesture synthesizer, the timing behaviours and the behaviour profiles. What remains, in dependency order:

  1. Calibrate the frame probe's thresholds — smooth_ms, intolerable_ms, jank_tolerance — against something defensible rather than leaving the placeholders in the output.
  2. Re-read the hierarchy per action, so the engine stops tapping stale coordinates after the screen changes, and give target choice a named policy object instead of i % len(targets).
  3. Exercise gestures live. Swipes dispatch as endpoint + duration over input swipe; replaying the curved path itself needs a sendevent/uiautomator2 driver — which is also what would consume the motion events of IF-C2-to-Driver.
  4. Escalate on repetition: consecutive stalls are counted and carried but provocation does not yet rise with them — the measured shape of rage-clicking, still unused by the cognitive layer.
  5. Version the output contract: add schema_version and a JSON Schema, so the timeline is still readable when the shared store finally exists.
  6. Fitts movement time in the timing model.
  7. EXP-02, the coupling ablation on an app made to misbehave (C1's stressors), then EXP-01 against a baseline tool — the experiments that would move CLAIM-01 past proposed.
